# GTX 1650 Ti, 4 GB: experimental Flash-Next setup

This is an opt-in source-build path for an already prepared ISTA-DASLab IQ3_XXS pack.
It does not download or convert a model. It does not change the released engine or the normal setup defaults.

## Why a smaller context alone may not help

On one GTX 1650 Ti laptop (Intel i5-10300H, 64 GB RAM, Linux), engine 0.1.59 loaded
1,466 MiB of canonical weights and 1,781 MiB of native projections, then failed with
`session state allocation failed`. With a 1K context, an allocation trace showed a
135 MiB session request failing with about 137 MiB reported free. A reported free count
is not a promise that the allocation fits. The local source build, with the new switch off,
also failed at 8K: 235 MiB requested, 136 MiB free.

`STRATA_WEIGHT_ARENA_HOST=1` keeps the canonical weight arena in pinned system RAM.
The same loader and kernels write and read its mapped device alias. Native projections,
working buffers and the expert cache still use VRAM. This does not requantize the weights.
The existing `STRATA_HEAD_HOST=1` switch also puts the output head in pinned RAM.
Every weight read across PCIe can be expensive. This is a way to test starting on a small
card, not a promise of speed or full model correctness.

The new switch accepts exactly `1`. It is off otherwise. It is implemented for one discrete
CUDA GPU only. HIP and Metal do not use it. Do not combine it with a layer split.
Pinned allocations can fail if the OS or driver cannot lock enough RAM.

## Build and run

From the source checkout, with a CUDA toolkit that supports sm_75:

```sh
cmake -S . -B build-gtx1650 -G Ninja -DCMAKE_BUILD_TYPE=Release \
  -DSTRATA_ENABLE_CUDA=ON -DCMAKE_CUDA_ARCHITECTURES=75 -DSTRATA_BUILD_TESTS=ON \
  -DSTRATA_PORTABLE=ON
cmake --build build-gtx1650 --target strata mapped_weight_arena_test \
  mapped_weight_cache_test native_dense_ple_key_test -j3
ctest --test-dir build-gtx1650 \
  -R '^(mapped_weight_(arena|cache)_test|native_dense_ple_key_test(_pooled)?)$' \
  --output-on-failure
```

Use a Python environment with Strata's server dependencies, such as the source checkout's
`.venv` or an installed Control package's bundled Python:

```sh
/path/to/python tools/run_gtx1650.py --data-dir /path/to/Strata-data
```

The data directory must already contain `packs/iq3_xxs` and both GGUF shards under
`models/IQ3_XXS`. The launcher reports missing files instead of downloading them.
It does not load an MTP or DFlash2 drafter.

It writes `build-gtx1650/gtx1650.json`, uses that local engine and serves on
`http://127.0.0.1:8080`. Stop with Ctrl+C. `--port 18080` chooses another port;
`--engine /path/to/strata` chooses another **patched** build.
`--write-config-only` writes the config without starting anything.

The profile uses 8K context, int8 KV, a 32-token prompt chunk with its own buffers,
a small expert cache (`--expert-cache 32`), three CPU workers, no drafter,
no lookup windows, no conversation parking and no pictures. `--spec 2` satisfies the native
pack's engine requirement; no draft model is loaded and the observed draft count was zero.
These are working starting settings, not a measured fastest configuration.
It writes a separate config and does not replace the app's model config or engine packages.
Do not increase context or turn pictures on until a real response works with these settings.

## Opt-in faster profile

The original configuration is still the default (`--profile stable`). On the tested laptop,
`--profile fast` keeps the output head in VRAM when it fits, enables the engine's Turing
kernel series, raises the prompt chunk from 32 to 256, and uses the batched path for short
prompts. It does not add HC requantization, reduce context, or change KV precision.

```sh
/path/to/python tools/run_gtx1650.py --data-dir /path/to/Strata-data --profile fast
```

It writes `gtx1650-fast.json` and `gtx1650-fast.engine.log` beside the engine, separate from
the stable files. The tested fast start left 256 MiB free instead of stable's 744 MiB.
If another program uses the GPU and fast fails, return to `--profile stable`.
If you exported `STRATA_HEAD_HOST`, unset it to test the measured GPU-head configuration.
Short prompts now use another arithmetic order, so output need not be bitwise identical.

Same laptop, same engine and model, three rounds per configuration, thinking off:
64-token English and Arabic answers decoded at a median 4.9 -> 5.8 tok/s;
a fresh 231-token prompt read at 14.4 -> 35.6 tok/s, with total request time
16.41 -> 6.83 s. Those are small local workloads, not general quality or speed guarantees.
A separate 5,892-token recall request and six short chat/JSON/tool checks also passed.
Full results, settings, failures and limits: [tuning report](../bench/results/2026-11-13-gtx1650ti-4gb-tuning/README.md).

For fresh-prompt measurements add `--no-prompt-cache`, then run
`python tools/bench_gtx1650.py --label fast --rounds 3 --out /tmp/gtx-fast.jsonl`.
Leave out `--no-prompt-cache` for normal chat. The benchmark does not start or stop the server
and does not measure streaming time to first token. Its output includes all responses and errors.

## Second tuning pass: exact-byte cache and a separate HC Q8 option

The existing `stable` and `fast` generated settings and stdout remain byte-identical to the
previous launcher. Two new profiles use separate config and log files:

```sh
/path/to/python tools/run_gtx1650.py --data-dir /path/to/Strata-data --profile cached
# Only if accepting additional HC requantization:
/path/to/python tools/run_gtx1650.py --data-dir /path/to/Strata-data --profile hc-q8
```

Stop the current server before starting another on the same port.

`cached` starts from `fast`, enables `STRATA_NATIVE_POOL=1` to pack immutable CUDA allocations
more tightly, and requests `STRATA_WEIGHT_CACHE_MIB=160`. The cache copies whole tensors into
VRAM before binding sessions/graphs, without changing their bytes. The actual prefix was
159.94 MiB / 53 tensors. Uncached tensors remain mapped in pinned RAM.
A nonzero cache requires one discrete CUDA GPU and mapped host weights; valid budgets are
0–1024 MiB. The pooled native allocator needs CUDA 11.2+ and device memory-pool support.
The pooled allocator rejects unsupported requests rather than silently selecting another backend.

`hc-q8` enables pooled allocations and the engine's existing `STRATA_HC_Q8=1` path, forces the
head into host RAM, uses expert cache 8 and prefill 128. **It changes HC weight precision to
Q8_0.** It is not an equal-precision comparison and is not the unchanged-weight recommendation.
Neither new profile downloads or rewrites the GGUF files. Both retain 8K context, int8 KV
and three workers. Ambient exported engine variables can still change a profile's behavior;
check `STRATA_HEAD_HOST`, `STRATA_HC_Q8` and other tuning overrides before reproducing it.

Same new engine binary, same laptop/model, three rounds per profile, fresh prompts:

| Metric | `fast` | `cached` | `hc-q8` — changes HC precision |
| --- | ---: | ---: | ---: |
| English / Arabic decode, tok/s | 5.9 / 5.9 | 6.3 / 6.3 | 8.8 / 8.8 |
| English 64-token request, seconds | 12.7445 | 12.1200 | 9.1318 |
| 231-token prompt, tok/s | 35.4 | 35.8 | 33.8 |
| Free VRAM after loading, MiB | 256 | 274 | 276 |

These are medians, not peak rates or broad quality results. Small prompt-speed differences
are not a demonstrated improvement. Memory figures are startup snapshots, not peak use.
The low memory margin still needs caution if other programs use the GPU.

Both new profiles passed 11 small sanity checks each, including a near-limit recall request:
8,169 prompt tokens plus 7 generated tokens, returning `violet-742`, with zero reused tokens.
They also passed a normal-checkpointing two-turn streaming conversation with 29 reused tokens
on the second turn. This is not a long-context quality evaluation or a TTFT benchmark.
Controlled old/new-disabled/cached window hashes matched on one 16-window teacher-forced
fixture with adaptation frozen and CPU prompt sharing disabled. That is not general output parity.

Source review of basalt and llamAmpere informed the memory-allocation and residency experiments.
Their Blackwell/Ampere kernels were not copied or benchmarked on this Turing card.
See the [second report](../bench/results/2026-11-13-gtx1650ti-4gb-pool-cache/README.md)
for pinned references, every experiment, raw responses, checks and limits.

## Third pass: decode-focused text chat (`hc-q8-decode`)

This opt-in profile keeps **the same HC Q8 precision as `hc-q8`**, but changes how prompts
are read so the output head can stay in VRAM. It does not download or replace a model.
The four older profiles, including the `stable` default, are unchanged.

```sh
/path/to/python tools/run_gtx1650.py --data-dir /path/to/Strata-data --profile hc-q8-decode
```

The new `STRATA_DECODE_ONLY_PROMPT=1` engine switch omits the batched prompt path's buffers
and cuBLAS handle. Every text prompt goes through the existing verify-window reader.
The launcher sets `--short-read 8192`, keeps the GPU output head, caches a 160 MiB prefix of
the mapped arena, fixes `--pcie-frac 0.5`, and lowers the cache-planning reserve to 128 MiB.
The actual cache was 158.41 MiB / 261 tensors. Cached bytes are unchanged; the HC Q8
requantization is still the separate precision change inherited from `hc-q8`.

The engine rejects this mode with a layer split, integrated GPU, batch, pictures, MTP/DFlash2,
a peer/helper GPU, pipelined windows, checkpoint-reread diagnostics, or borrowed prompt buffers.
`--short-read` must cover the configured context. A request that still needs the batched
reader returns an error rather than touching uninitialized buffers. The mode is experimental
CUDA only; it is not enabled in HIP/Metal or the separate SYCL engine.

**There is a tradeoff.** Same laptop/model, final CUDA binary, three rounds each on
14 November 2026, thinking off and zero reused tokens:

| Metric | `hc-q8` remeasured | `hc-q8-decode` |
| --- | ---: | ---: |
| English decode, tok/s | 9.2 | **15.5** |
| Arabic decode, tok/s | 9.2 | **15.4** |
| English 64-token request, seconds | 8.7590 | 6.0429 |
| Arabic 64-token request, seconds | 8.7334 | 6.0794 |
| 231-token prompt reading, tok/s | **33.8** | 22.2 |
| Same filler/capital request, seconds | **7.0540** | 10.5290 |
| Free VRAM at startup, MiB | **277** | 149 |
| Context / KV | 8192 / int8 | 8192 / int8 |

Decode improved about 68% on these two short output workloads, **not every request**.
The longer input was slower overall. The new window reader also changes prompt arithmetic
relative to batched reading; this is not a proof of unchanged answer quality.

149 MiB is a **LOW-memory warning**, not a comfortable margin; graph captures use more.
The 128 MiB planning reserve is not a guaranteed free-memory floor. This profile refuses a
host-head fallback (`STRATA_HEAD_HOST_OFF=1`); unset an exported `STRATA_HEAD_HOST` before using it.
Close other GPU programs. If it fails or long-input latency matters more, use `hc-q8` or
`cached` instead. Keep `--no-prompt-cache` for measurement only; omit it for normal chat.

Raw requests, failed experiments, build details, checks and limits:
[third tuning report](../bench/results/2026-11-14-gtx1650ti-4gb-decode-residency/README.md).
These are local exploratory results, not a standard protocol run or a comparison against GTX 1070.

## Initial checks and current limits

Tested locally on the GTX 1650 Ti above, CUDA 13.4.92, driver 620.70.06, source revision
`13eedf55` plus this patch, engine 0.1.59.1:

- CUDA build and `mapped_weight_arena_test`: passed. The test writes through the loader's
  H2D copy path and reads every byte from a captured GPU kernel. This tests addressing,
  not language-model quality.
- `python tools/test_run_gtx1650.py`: two config-generation tests passed, without a GPU.
- The local HTTP server reached `/health` with `loaded: true`, context 8192, images off.
  Its startup log reported 744 MiB of VRAM free after loading.
- Four non-streaming Chat Completions requests across two server starts, temperature 0,
  thinking off, passed:

| Prompt | Prompt tokens | Answer | Total request time |
| --- | ---: | --- | ---: |
| 2 + 2, number only | 26 | `4` | 4.53 s |
| Saudi Arabia's capital, in Arabic | 26 | `عاصمة السعودية هي الرياض.` | 4.75 s |
| Repeated filler followed by France's capital | 242 | `Paris` | 17.29 s |
| `hi` (after restarting the server) | 13 | `Hi there! How can I help you today?` | 3.79 s |

These are single smoke requests with very short answers, not a throughput or quality benchmark.
A 128-token chunk with an automatic cache and DFlash2 failed to start even with mapped weights;
the smaller, drafter-free profile above is what passed. The initial test server was stopped;
a later restart also passed the `hi` request.
The stock route-tail skip and CPU prompt-share policies were not changed; mapped storage alone
does not establish bitwise model-output parity.

The later near-limit checks above used 8,169 prompt tokens in each new profile.
Not run: an exact 8192-position boundary, a long soak, pictures, parallel requests, other cards,
Windows, or HIP/SYCL/Metal builds. Those compiler toolchains were unavailable for the second pass.
Four targeted CUDA tests and four Python tests passed after the new changes.
This is a local experimental change, not a cross-backend validated PR.
