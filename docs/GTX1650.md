# GTX 1650 Ti, 4 GB: experimental Flash-Next setup

This is an opt-in source-build path for an already prepared ISTA-DASLab IQ3_XXS pack.
It does not download or convert a model. It does not change the released engine or the normal setup defaults.

## Why a smaller context alone may not help

On one GTX 1650 Ti laptop (Intel i5-10300H, 64 GB RAM, Linux), engine 0.1.59 loaded
1,466 MiB of canonical weights and 1,781 MiB of native projections, then failed with
`session state allocation failed`. With a 1K context, an allocation trace showed a
135 MiB session request failing with about 137 MiB reported free. A reported free count
is not a promise that the allocation fits. The local source build, with the new switch off,
also failed at 8K: 235 MiB requested, 136 MiB free.

`STRATA_WEIGHT_ARENA_HOST=1` keeps the canonical weight arena in pinned system RAM.
The same loader and kernels write and read its mapped device alias. Native projections,
working buffers and the expert cache still use VRAM. This does not requantize the weights.
The existing `STRATA_HEAD_HOST=1` switch also puts the output head in pinned RAM.
Every weight read across PCIe can be expensive. This is a way to test starting on a small
card, not a promise of speed or full model correctness.

The new switch accepts exactly `1`. It is off otherwise. It is implemented for one discrete
CUDA GPU only. HIP and Metal do not use it. Do not combine it with a layer split.
Pinned allocations can fail if the OS or driver cannot lock enough RAM.

## Build and run

From the source checkout, with a CUDA toolkit that supports sm_75:

```sh
cmake -S . -B build-gtx1650 -G Ninja -DCMAKE_BUILD_TYPE=Release \
  -DSTRATA_ENABLE_CUDA=ON -DCMAKE_CUDA_ARCHITECTURES=75 -DSTRATA_BUILD_TESTS=ON \
  -DSTRATA_PORTABLE=ON
cmake --build build-gtx1650 --target strata mapped_weight_arena_test -j3
ctest --test-dir build-gtx1650 -R '^mapped_weight_arena_test$' --output-on-failure
```

Use a Python environment with Strata's server dependencies, such as the source checkout's
`.venv` or an installed Control package's bundled Python:

```sh
/path/to/python tools/run_gtx1650.py --data-dir /path/to/Strata-data
```

The data directory must already contain `packs/iq3_xxs` and both GGUF shards under
`models/IQ3_XXS`. The launcher reports missing files instead of downloading them.
It does not load an MTP or DFlash2 drafter.

It writes `build-gtx1650/gtx1650.json`, uses that local engine and serves on
`http://127.0.0.1:8080`. Stop with Ctrl+C. `--port 18080` chooses another port;
`--engine /path/to/strata` chooses another **patched** build.
`--write-config-only` writes the config without starting anything.

The profile uses 8K context, int8 KV, a 32-token prompt chunk with its own buffers,
a small expert cache (`--expert-cache 32`), three CPU workers, no drafter,
no lookup windows, no conversation parking and no pictures. `--spec 2` satisfies the native
pack's engine requirement; no draft model is loaded and the observed draft count was zero.
These are working starting settings, not a measured fastest configuration.
It writes a separate config and does not replace the app's model config or engine packages.
Do not increase context or turn pictures on until a real response works with these settings.

## Opt-in faster profile

The original configuration is still the default (`--profile stable`). On the tested laptop,
`--profile fast` keeps the output head in VRAM when it fits, enables the engine's Turing
kernel series, raises the prompt chunk from 32 to 256, and uses the batched path for short
prompts. It does not add HC requantization, reduce context, or change KV precision.

```sh
/path/to/python tools/run_gtx1650.py --data-dir /path/to/Strata-data --profile fast
```

It writes `gtx1650-fast.json` and `gtx1650-fast.engine.log` beside the engine, separate from
the stable files. The tested fast start left 256 MiB free instead of stable's 744 MiB.
If another program uses the GPU and fast fails, return to `--profile stable`.
If you exported `STRATA_HEAD_HOST`, unset it to test the measured GPU-head configuration.
Short prompts now use another arithmetic order, so output need not be bitwise identical.

Same laptop, same engine and model, three rounds per configuration, thinking off:
64-token English and Arabic answers decoded at a median 4.9 -> 5.8 tok/s;
a fresh 231-token prompt read at 14.4 -> 35.6 tok/s, with total request time
16.41 -> 6.83 s. Those are small local workloads, not general quality or speed guarantees.
A separate 5,892-token recall request and six short chat/JSON/tool checks also passed.
Full results, settings, failures and limits: [tuning report](../bench/results/2026-11-13-gtx1650ti-4gb-tuning/README.md).

For fresh-prompt measurements add `--no-prompt-cache`, then run
`python tools/bench_gtx1650.py --label fast --rounds 3 --out /tmp/gtx-fast.jsonl`.
Leave out `--no-prompt-cache` for normal chat. The benchmark does not start or stop the server
and does not measure streaming time to first token. Its output includes all responses and errors.

## Checks and limits

Tested locally on the GTX 1650 Ti above, CUDA 13.4.92, driver 620.70.06, source revision
`13eedf55` plus this patch, engine 0.1.59.1:

- CUDA build and `mapped_weight_arena_test`: passed. The test writes through the loader's
  H2D copy path and reads every byte from a captured GPU kernel. This tests addressing,
  not language-model quality.
- `python tools/test_run_gtx1650.py`: two config-generation tests passed, without a GPU.
- The local HTTP server reached `/health` with `loaded: true`, context 8192, images off.
  Its startup log reported 744 MiB of VRAM free after loading.
- Four non-streaming Chat Completions requests across two server starts, temperature 0,
  thinking off, passed:

| Prompt | Prompt tokens | Answer | Total request time |
| --- | ---: | --- | ---: |
| 2 + 2, number only | 26 | `4` | 4.53 s |
| Saudi Arabia's capital, in Arabic | 26 | `عاصمة السعودية هي الرياض.` | 4.75 s |
| Repeated filler followed by France's capital | 242 | `Paris` | 17.29 s |
| `hi` (after restarting the server) | 13 | `Hi there! How can I help you today?` | 3.79 s |

These are single smoke requests with very short answers, not a throughput or quality benchmark.
A 128-token chunk with an automatic cache and DFlash2 failed to start even with mapped weights;
the smaller, drafter-free profile above is what passed. The initial test server was stopped;
a later restart also passed the `hi` request.
The stock route-tail skip and CPU prompt-share policies were not changed; mapped storage alone
does not establish bitwise model-output parity.

Not run: a full 8K prompt, a long soak, pictures, parallel requests, other cards, HIP, SYCL
or Metal builds. This is a local experimental change, not a cross-backend validated PR.

## Community examples consulted

- [Righteous-AI/Strata-Recipes](https://github.com/Righteous-AI/Strata-Recipes),
  revision `b7d70b032918`: RTX 5090, NVFP4, DFlash2 and memory tuning.
- [ExTV/strata-5090-4070](https://github.com/ExTV/strata-5090-4070),
  revision `352dc9f8b087`: a 32 GB + 16 GB layer split, prompt placement and RAM/SSD tuning.

Those are different machines and workloads. Their patch series and performance numbers do
not establish support for a 4 GB GTX. No patches from those older upstream revisions are
applied here. The related startup report is [#5513](https://github.com/Niko1221/Strata/issues/5513).
